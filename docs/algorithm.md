# 算法与实现边界

## 输入约定：配对合成，而非目标分割

网页要求输入已准备好的单色背景彩色图和配对灰度遮罩；它不从复杂场景中识别目标、不提供物体选择或语义分割，也不根据原图自动求解 Alpha。代码从遮罩像素读取透明度，再结合已知底色估计前景颜色。

完整工作流中的主体选择、背景去除与遮挡内容重建由前面的生成或素材制作阶段完成。该阶段可能改变原图细节；后续网页合成不能验证或补回真实但不可见的内容，也不能修复两张输入之间的局部位移。

## 两个问题：透明度与前景颜色

灰度遮罩是 Alpha：0 表示背景，255 表示不透明，中间值表示部分覆盖或透明。它不是亮度图，也不是 Trimap。Trimap 的灰区表示“待求解”，并不提供最终透明度。

普通合成方程逐通道写作 `I = αF + (1−α)B`。我们把生成图的背景设为已知常量，试图降低背景估计难度。给定 Alpha，反解为 `F = (I−(1−α)B)/α`；Alpha 为 0 时没有可恢复的前景信息。

Alpha 与背景色都来自实际输入，并不天然准确。α 越小，除法对误差的放大越明显。例如 α=0.05 时，输入误差会被放大约 20 倍。RGB 裁到 0…255 后可能不可逆。

## 现有网页实际做了什么

源码见 [app.js](../src/app.js)。

1. 读取 Canvas 像素，从灰度遮罩估计 Alpha。非中性遮罩使用亮度与最大通道的组合，是历史容错处理；推荐输入真正的单通道中性灰度图。
2. 按黑场/白场设置压缩 Alpha 端点。通用预设不裁端点。
3. 从指定纯色（默认 128,128,128）或边框中位数得到底色。主体占满边缘时不应使用边框估计。
4. 用合成方程反推 RGB，限制取值；再按 Alpha、亮度和“灰底反推”强度，与输入 RGB 做受限混合。即使滑杆设为 1，也不是严格全量反解。
5. 白纱中和以遮罩和亮度构造偏白、微蓝的候选色；灰边清理按像素距底色的差异降低 Alpha。两者都是经验修正，会改变素材。
6. 导出非预乘形式的 RGBA PNG；浏览器内部如何存储与转换 Canvas 像素由浏览器管理。全透明 RGB 可置零。

本实现直接在 Canvas 返回的 8 位 RGB 数值上计算，没有显式 sRGB 到线性光转换。应将它视为现有工作流的视觉调节工具，而不是线性光空间中的物理精确求解器。

## 首版预设

| 参数 | 通用 | 白纱历史参数 |
|---|---:|---:|
| 黑场裁切 | 0 | 0.004 |
| 白场压实 | 1 | 0.992 |
| 灰底反推 | 0.90 | 0.90 |
| 灰边清理 | 0 | 0.95 |
| 白纱中和 | 0 | 0.72 |

通用预设保留输入 Alpha，不等于完全保留 RGB。白纱预设会对低 Alpha 的颜色和透明度做额外处理。既不能把“灰度更丰富”当成更准确，也不能仅看棋盘格背景判断没有底色污染。

## 特效、折射与多层材质

发光通常含加法成分，玻璃会折射背景，重叠薄纱含多层传输。单层普通 Alpha 不足以在任意新背景中还原所有这些效果。法器案例保留为探索性演示；黑底和白底效果必须都公开，不只挑有利底色。

## 质检能证明什么

辅助脚本可证明尺寸、文件模式、黑白端点，以及零遮罩区域的底色精确；不能证明 Alpha 真实、身份完全不变、薄纱透光率准确或所有轮廓逐像素正确。红线叠加提供人工检查依据，不是自动对齐证书。

本项目使用通用的前景/背景/Alpha 合成关系，重点在配对素材准备、验收与交付流程以及本地网页实现；不包含新的神经网络，也没有与其他方法进行受控 benchmark。
